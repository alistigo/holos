# Task: Write ADR 0024 + ADR 0025

## Description

Document the two key architectural decisions for this epic before implementation begins.

**ADR 0024 — Shared-List View: Actor Registry in Document**
File: `docs/adrs/0024-shared-list-view-actor-registry.md`

Decision: Store a denormalized `alistigo:actors` section directly in the list document (not in the plugin store at render time). The user plugin's `user:changed` event triggers the artifact-list host to write public actor info (actorId, userId, pseudo, avatar) into the document before serialization. Attribution (avatar + pseudo + relative date) is shown per element when ≥2 distinct user actors are in the document. Relative date uses `date-fns` `formatDistanceToNow`.

Rationale to cover:
- Why denormalized in document (not plugin store lookup at render time) — documents must be self-contained for offline use and for future export/share scenarios
- Why `user:changed` not `user:setup` — covers identity updates mid-session
- Why `date-fns` over `timeago.js` / `dayjs` (tree-shakeable, already common in TS projects)
- Why attribution conditional on ≥2 user actors — solo users should see no extra UI

**ADR 0025 — Checkbox Plugin: First Domain-Contribution Plugin**
File: `docs/adrs/0025-checkbox-plugin-domain-contribution.md`

Decision: Domain-contribution plugins own their event types, reducers, and UI render zones. The base document schema accepts new event types via an open enum (or union type extension). Each plugin declares `metadataKey`, `reduce(elementMeta, event)`, and `renderListElementLeading(elementId, meta, onCommand)`. The host replays events through `plugin.reduce()` to build per-element metadata state. This activates the forward-compat stubs added in ADR 0016.

Rationale to cover:
- Why reducer pattern (not mutable state) — reproducible from event log, testable pure functions
- Why `alistigo:metadatas` per element vs a top-level metadata map — keeps element data co-located
- Why plugin declares its metadata key — prevents key collisions across plugins
- Why `renderListElementLeading` (not `renderListItem`) — gives plugins a bounded slot, not full item ownership
- Why `alistigo:plugins` at document root — documents need to declare what plugins are active for correct replay
